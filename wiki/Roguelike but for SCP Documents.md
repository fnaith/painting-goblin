# 遊戲流程

## 1. 接收未知異常體

- 異常體被送入標準化收容倉。
- 玩家僅知道最基本資訊（外觀、事故紀錄等）。

## 2. 觀察異常體

- 透過監視器、感測器等設備觀察異常體。
- 獲得初步線索。

## 3. 進行實驗

- 使用有限的設備與資源測試異常體。
- 每次實驗都會消耗資源，並提高異常體活性。
- 取得新的觀察結果。

## 4. 分析結果

- 根據觀察與實驗結果，推測異常體的規則。
- 玩家可選擇繼續研究，或停止研究。

## 5. 制定收容方案

- 根據目前掌握的資訊，設計異常體的收容程序。
- 配置適當的收容措施（照明、隔音、溫度、餵食、限制行為等）。
- 收容措施越多，成本越高；越精簡，失敗風險越高。

## 6. 執行收容

- 系統模擬收容結果。
- 若收容方案正確，異常體成功收容。
- 若缺少關鍵措施，異常體可能突破收容並造成損失。

## 7. 結算

根據以下項目進行評分與獎勵：

- 收容是否成功
- 收容成本
- 研究完整度
- 剩餘資源

# 評分標準
每個措施都有成本

例如：

- 收容措施	成本
- 全天照明	1
- 隔音	2
- UV照射	3
- 法拉第籠	4
- 自動麻醉	5
- 緊急焚毀	8

最後玩家提交的其實是一份配置，例如：

A-017 收容程序

✓ 全天照明
✓ UV照射
✓ 禁止交談
✓ 遠端操作

總成本：8

系統會驗證：

必要措施是否都有？（少一項就可能突破收容）
是否有多餘措施？（增加成本、降低評價）

這樣評分就很自然：

S：成功收容，且成本接近理論最低。
A：成功收容，但有少量冗餘措施。
B：成功收容，但大量過度設計。
C：勉強收容，依賴高成本緊急措施。
D：突破收容。

我認為這種「收容方案組裝（Containment Loadout）」會是你遊戲最有特色的部分，因為玩家最後不是交一份報告，而是真正設計一套可以執行的收容程序。

# 可系統化推導規則（觀察 → 收容需求）

## 一、核心概念

玩家不直接獲得「收容需求」，而是透過：

> 觀察事件 → 行為分類 → 推導需求 → 生成收容方案

## 二、觀察標準化（事件對）

所有資料必須轉換為：

```
（觸發條件）→（異常反應）
```

### 例子：

- 關燈 → 異常體移動
- 人聲出現 → 攻擊行為
- UV照射 → 行為停止

## 三、觀察分類（四種事件標籤）

| 類型 | 說明 | 問題 |
|------|------|------|
| 狀態依賴 | 缺少某狀態會異常 | 它需要什麼存在？ |
| 壓制反應 | 某條件會降低活性 | 什麼能削弱它？ |
| 觸發反應 | 某條件會導致暴走 | 什麼會刺激它？ |
| 緊急恢復 | 可用於失控後控制 | 什麼能救場？ |

## 四、需求推導規則（核心轉換）

### 1. 生存需求（Survival Requirement）

來源：狀態依賴

```
若缺少 X → 異常體失控或異常
⇒ X = 生存需求
```

### 例子：

- 無UV → 行為崩壞
⇒ 生存需求：UV照射

### 2. 限制需求（Constraint Requirement）

來源：壓制反應

```
若存在 X → 活性下降 / 穩定
⇒ X = 限制需求
```

### 例子：

- 安靜環境 → 活動減少
⇒ 限制需求：隔音

### 3. 觸發需求（Trigger Condition）

來源：觸發反應

```
若出現 X → 異常體暴走 / 升級
⇒ X = 觸發條件（需避免）
```

### 例子：

- 人聲 → 攻擊行為
⇒ 觸發需求：禁止人聲

### 4. 保險措施（Safety / Backup）

來源：緊急恢復

```
若使用 X → 可恢復控制狀態
⇒ X = 保險措施
```

### 例子：

- 麻醉氣體 → 恢復穩定
⇒ 保險措施：麻醉系統

## 五、可信度計算（防止猜答案）

```
可信度 = 出現頻率 × 一致性 × 危險程度
```

| 指標 | 說明 |
|------|------|
| 出現頻率 | 是否重複觀察 |
| 一致性 | 是否每次都成立 |
| 危險程度 | 失誤後果嚴重性 |

### 範例：

| 觀察 | 推論 | 可信度 |
|------|------|--------|
| UV停止活動 | 生存需求 | 0.9 |
| 安靜降低活動 | 限制需求 | 0.6 |
| 人聲觸發攻擊 | 觸發需求 | 0.95 |
| 麻醉可恢復控制 | 保險措施 | 0.8 |

## 六、需求 → 收容方案轉換

| 需求類型 | 玩家行為 |
|----------|----------|
| 生存需求 | 必須配置 |
| 限制需求 | 建議配置 |
| 觸發需求 | 必須封鎖或避免 |
| 保險措施 | 緊急備援 |

## 七、最終輸出（玩家收容設計）

```yaml
生存需求：
- UV照射

限制需求：
- 隔音

觸發需求：
- 禁止人聲進入收容室

保險措施：
- 麻醉氣體系統
```

## 八、設計原則

- 玩家永遠不會直接看到「正確答案」
- 只能看到「觀察結果 + 機率推論」
- 不同異常體共用同一推理框架
- 差異只在「證據組合」，不是規則系統

## 九、核心循環

```
觀察 → 分類 → 推導 → 設計收容 → 測試結果 → 修正模型
```

## 一句話總結

> 透過事件分類與規則映射，將觀察結果系統化轉換為四種收容需求，使玩家學習的是推理方法，而非固定答案。

## UI 設計原則

1. 主畫面永遠聚焦於異常體。
2. 同一時間只開啟一個 Popup，避免資訊過載。
3. 所有研究資料自動記錄，玩家負責推理，不需要手動做筆記。
4. 收容方案以模組化方式配置，立即顯示成本。
5. 異常體活性提高時，主畫面直接反映（燈光閃爍、監視器干擾、警報），而不是透過更多 UI 提示。

# 異常體案例：A-001「凝視者」

## 基本資料

- 編號：A-001
- 名稱：凝視者
- 類型：認知干擾型 / 靜態觀察型
- 收容等級：低風險（初期）
- 異常描述：人形輪廓黑影，長時間靜止站立於收容室中央

## 初始事件記錄（事故報告）

> 運輸途中發生兩名警衛精神崩潰，未見物理攻擊痕跡。

推測：

- 可能為認知影響型異常體
- 或透過感知／觀察觸發影響

## 觀察紀錄（原始數據）

### 觀察 01

```
狀態：燈光關閉
結果：異常體開始緩慢轉向攝影機
```

### 觀察 02

```
狀態：燈光開啟
結果：異常體停止移動
```

### 觀察 03

```
狀態：UV照射
結果：異常體後退並降低活動
```

### 觀察 04

```
狀態：播放人聲
結果：異常體轉向聲源（喇叭）
```

### 觀察 05

```
狀態：白噪音
結果：無明顯反應
```

## 行為推論（玩家未確認）

| 觀察條件 | 推測效果 | 信心 |
|-----------|----------|------|
| 黑暗 | 促進活動 | 0.75 |
| 光照 | 抑制活動 | 0.85 |
| UV | 強力抑制 | 0.90 |
| 人聲 | 注意／定向反應 | 0.80 |
| 白噪音 | 無效刺激 | 0.60 |

## 推導出的收容需求（系統推論）

### 生存需求（可能）

- 無（未確認存在必要維持條件）

### 限制需求（核心）

- 強光照明（持續）
- UV照射（間歇或持續）

### 觸發需求（危險條件）

- 人聲暴露（高優先風險）
- 低光環境（活動提升）

### 保險措施（備援）

- 麻醉氣體

## 收容結果（測試模擬）

### 成功條件

- 光照維持
- UV持續或間歇
- 避免人聲刺激

### 失敗條件

- 黑暗環境持續超過閾值
- 人聲直接暴露（未隔離）
- UV設備失效

## 設計重點

- 此異常體不具直接攻擊能力
- 危險來源為「感知觸發型行為變化」
- 核心挑戰為「環境控制優化」而非戰鬥
