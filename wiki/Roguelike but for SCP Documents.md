# 遊戲流程

## 1. 接收未知異常體

- 異常體被送入標準化收容倉。
- 玩家僅知道最基本資訊（外觀、事故紀錄等）。

## 2. 觀察異常體

- 透過監視器、感測器等設備觀察異常體。
- 獲得初步線索。

## 3. 進行實驗

- 使用有限的設備與資源測試異常體。
- 每次實驗都會消耗資源，並提高異常體活性。
- 取得新的觀察結果。

## 4. 分析結果

- 根據觀察與實驗結果，推測異常體的規則。
- 玩家可選擇繼續研究，或停止研究。

## 5. 制定收容方案

- 根據目前掌握的資訊，設計異常體的收容程序。
- 配置適當的收容措施（照明、隔音、溫度、餵食、限制行為等）。
- 收容措施越多，成本越高；越精簡，失敗風險越高。

## 6. 執行收容

- 系統模擬收容結果。
- 若收容方案正確，異常體成功收容。
- 若缺少關鍵措施，異常體可能突破收容並造成損失。

## 7. 結算

根據以下項目進行評分與獎勵：

- 收容是否成功
- 收容成本
- 研究完整度
- 剩餘資源

# 評分標準
每個措施都有成本

例如：

- 收容措施	成本
- 全天照明	1
- 隔音	2
- UV照射	3
- 法拉第籠	4
- 自動麻醉	5
- 緊急焚毀	8

最後玩家提交的其實是一份配置，例如：

A-017 收容程序

✓ 全天照明
✓ UV照射
✓ 禁止交談
✓ 遠端操作

總成本：8

系統會驗證：

必要措施是否都有？（少一項就可能突破收容）
是否有多餘措施？（增加成本、降低評價）

這樣評分就很自然：

S：成功收容，且成本接近理論最低。
A：成功收容，但有少量冗餘措施。
B：成功收容，但大量過度設計。
C：勉強收容，依賴高成本緊急措施。
D：突破收容。

我認為這種「收容方案組裝（Containment Loadout）」會是你遊戲最有特色的部分，因為玩家最後不是交一份報告，而是真正設計一套可以執行的收容程序。

# 遊戲系統

## 異常體規則層

| 類型   | 本質          | 例子      |
| ---- | ----------- | ------- |
| 生存需求 | 不滿足就無法收容    | 必須低溫    |
| 限制需求 | 降低風險 / 穩定行為 | 隔音      |
| 觸發需求 | 會引發異常反應的條件  | 聽到人聲會暴走 |
| 保險措施 | 防止失控的備援     | 麻醉氣體    |

## 玩家操作層

| 類型   | 本質      | 例子      |
| ---- | ------- | ------- |
| 環境控制 | 調整環境狀態  | UV、溫度   |
| 隔離措施 | 阻斷感知/傳播 | 隔音、法拉第籠 |
| 限制裝置 | 直接限制行動  | 力場、拘束   |
| 維生裝置 | 提供資源維持  | 水、生物質   |
| 緊急裝置 | 失敗時補救   | 麻醉、焚毀   |

## 對應關係

| 異常體需求層 | 對應玩家收容層           |
| ------ | ----------------- |
| 生存需求   | 環境控制 / 隔離 / 限制裝置  |
| 限制需求   | 隔離措施 / 限制裝置       |
| 觸發需求   | 環境控制 / 隔離措施（避免觸發） |
| 保險措施   | 緊急裝置              |

# 可系統化推導規則（觀察 → 收容需求）

## 一、核心概念

玩家不直接獲得「收容需求」，而是透過：

> 觀察事件 → 行為分類 → 推導需求 → 生成收容方案

## 二、觀察標準化（事件對）

所有資料必須轉換為：

```
（觸發條件）→（異常反應）
```

### 例子：

- 關燈 → 異常體移動
- 人聲出現 → 攻擊行為
- UV照射 → 行為停止

## 三、觀察分類（四種事件標籤）

| 類型 | 說明 | 問題 |
|------|------|------|
| 狀態依賴 | 缺少某狀態會異常 | 它需要什麼存在？ |
| 壓制反應 | 某條件會降低活性 | 什麼能削弱它？ |
| 觸發反應 | 某條件會導致暴走 | 什麼會刺激它？ |
| 緊急恢復 | 可用於失控後控制 | 什麼能救場？ |

## 四、需求推導規則（核心轉換）

### 1. 生存需求（Survival Requirement）

來源：狀態依賴

```
若缺少 X → 異常體失控或異常
⇒ X = 生存需求
```

### 例子：

- 無UV → 行為崩壞
⇒ 生存需求：UV照射

### 2. 限制需求（Constraint Requirement）

來源：壓制反應

```
若存在 X → 活性下降 / 穩定
⇒ X = 限制需求
```

### 例子：

- 安靜環境 → 活動減少
⇒ 限制需求：隔音

### 3. 觸發需求（Trigger Condition）

來源：觸發反應

```
若出現 X → 異常體暴走 / 升級
⇒ X = 觸發條件（需避免）
```

### 例子：

- 人聲 → 攻擊行為
⇒ 觸發需求：禁止人聲

### 4. 保險措施（Safety / Backup）

來源：緊急恢復

```
若使用 X → 可恢復控制狀態
⇒ X = 保險措施
```

### 例子：

- 麻醉氣體 → 恢復穩定
⇒ 保險措施：麻醉系統

## 五、可信度計算（防止猜答案）

```
可信度 = 出現頻率 × 一致性 × 危險程度
```

| 指標 | 說明 |
|------|------|
| 出現頻率 | 是否重複觀察 |
| 一致性 | 是否每次都成立 |
| 危險程度 | 失誤後果嚴重性 |

### 範例：

| 觀察 | 推論 | 可信度 |
|------|------|--------|
| UV停止活動 | 生存需求 | 0.9 |
| 安靜降低活動 | 限制需求 | 0.6 |
| 人聲觸發攻擊 | 觸發需求 | 0.95 |
| 麻醉可恢復控制 | 保險措施 | 0.8 |

## 六、需求 → 收容方案轉換

| 需求類型 | 玩家行為 |
|----------|----------|
| 生存需求 | 必須配置 |
| 限制需求 | 建議配置 |
| 觸發需求 | 必須封鎖或避免 |
| 保險措施 | 緊急備援 |

## 七、最終輸出（玩家收容設計）

```yaml
生存需求：
- UV照射

限制需求：
- 隔音

觸發需求：
- 禁止人聲進入收容室

保險措施：
- 麻醉氣體系統
```

## 八、設計原則

- 玩家永遠不會直接看到「正確答案」
- 只能看到「觀察結果 + 機率推論」
- 不同異常體共用同一推理框架
- 差異只在「證據組合」，不是規則系統

## 九、核心循環

```
觀察 → 分類 → 推導 → 設計收容 → 測試結果 → 修正模型
```

## 一句話總結

> 透過事件分類與規則映射，將觀察結果系統化轉換為四種收容需求，使玩家學習的是推理方法，而非固定答案。
```
